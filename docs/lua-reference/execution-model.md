## Сценарий: вычисление Lua и исполнение очереди

Порядок авторских фраз определяет сцену. Компилятор добавляет вход фразы, её персонажей/размещение, блоки «До», показ текста, блоки «Во время», неявное ожидание продолжения и блоки «После продолжения». Ещё есть начало/конец сцены. Блоки привязаны к стабильному ID фразы; перестановка/копирование/удаление в редакторе сохраняет или осмысленно заменяет связи. Импортированный старый произвольный поток не смешивается с этой моделью автоматически.

Сценарный блок или ресурс `game.run` каждый раз получает **новую VM** с `game` и своими `refs`. Сначала Lua вычисляет весь блок и формирует список команд. Потом host проверяет весь результат и вставляет его перед оставшейся очередью. Только затем команды исполняются по порядку. `return` ресурса не возвращает данные другому ресурсу; функция `game.run` возвращает nil и ставит команду будущего вызова.

```lua
game.wait(1)
game.set("ready", "true")
local value = game.get("ready") -- уже "true" в рабочей копии VM
```

Lua вычислит все три строки сразу. Игрок увидит изменение переменной лишь после исполнения секундного ожидания очереди. В отличие от set/get, `game.object`, `game.visible`, `game.time`, `game.minigame_result` читают исходный снимок и не симулируют подготовленные команды. `game.wait_input` также не приостанавливает Lua-стек. Поэтому цикл Lua с wait не является игровым циклом и обычно упрётся в квоты.

Чтобы обработать результат ожидания/мини-игры, поместите код **в следующий исполняемый блок или вызванный ресурс**. Запись `game.start_minigame(...); local r=game.minigame_result()` читает прежний снимок. Правильно: поставить запуск, затем `game.run(refs.after)`; ресурс after исполнится после барьера и получит новый снимок. У `game.run` самого отложенного возвращаемого значения нет: связь — переменные и очереди.

Во время pending сценарного Lua позиция остаётся перед действием. Host продолжает рисовать кадры, но время/движения/сценарный звук удерживаются; сохранить busy-прохождение нельзя. Готовый ответ применяется только на потоке host и только при совпадении поколения/снимка. Пауза удерживает и готовый ответ. Неудачный Load не отменяет действительную старую работу; успешный Load/NewGame/переход с отменой/закрытие её инвалидирует.

## Интерфейс: обработчик экземпляра

Lua-ресурс обработчика холста возвращает таблицу:

```lua
return {
  input_events = true, -- необязательно, по умолчанию false
  on_load = function(e) -- необязательно; e — пустая таблица
    ui.set_text(refs.label, "Привет")
  end,
  on_event = function(e) -- обязательно, именно Lua function
    if e.kind == "click" and e.node == refs.button then
      ui.set_text(refs.label, "Нажато")
    end
  end
}
```

Назначьте ресурс обработчиком сцены; label/button — именованные ссылки холста. Действие кнопки для click — Lua. У корневой сцены и каждого открытого слоя/мини-игры отдельный экземпляр с собственной VM. Вычисление исходника и on_load — разные этапы. При вычислении можно объявлять функции, импортировать модули, пользоваться ограниченной библиотекой и логировать. Выдавать команды вида/сервисов до возврата handlers нельзя. Состояние, RNG, анимации, звук и ввод дополнительно требуют активного обработчика.

VM интерфейса **сохраняется между событиями**, поэтому locals/замыкания/кеш модулей действительно живут. Но host не сериализует их и не откатывает как данные; после ошибки обработчик перестаёт принимать события. Долгоживущую игровую логику храните через `ui.set_state`, RNG — через управляемый поток, постоянные данные — через профиль. Не считайте local счётчик частью слота.

Разные VM интерфейса размещаются в **одном постоянном ui-worker** host-процесса, а не в отдельном процессе на экран. Он занимает одно из двух общих process-мест и одно из 34 admission-мест; рядом может работать сценарный worker. Изоляция глобальных таблиц не даёт каждому экрану отдельную квоту памяти/задержек: авария общей беседы может отключить всех её обработчиков.

`on_event` вызывается с одной таблицей [события](events.md). Прямого API подписки, таймера, sleep, coroutine или произвольной callback-функции для host нет. В актуальном runtime периодический `update` создаётся **для активной мини-игры**, с заданной частотой; обычный экран не получает гарантированный update-цикл. Его анимации исполняет host, а реакции приходят вводом, триггерами и результатами.

Все модули экземпляра используют те же ui-callbacks/рабочий state/RNG, но собственные globals и таблицы библиотеки. `game` в этом окружении отсутствует. См. [ресурсы и модули](modules.md).

## Пакет, ошибки и пределы отката

Изменяющие ui-вызовы подготавливают один пакет обработчика, максимум 256 команд. Worker последовательно проверяет промежуточные деревья и весь пакет, затем host повторно проверяет типы протокола, владельца/версию, состояние/схемы, бюджет очереди и резервы результатов. Публикация вида/state/RNG и старт операций происходят только в host Poll после полного принятия. Следующая команда в этом же обработчике может использовать скопированный узел или прочитать подготовленное set_state; это ещё не подтверждение host.

Ошибка аргумента, handle, Value, квоты или запрещённого сочетания отклоняет **весь пакет**. Прежние подтверждённые вид/state/RNG остаются. Ошибочный обработчик отключается, его работа/собственные источники очищаются. Ошибка общей IPC-беседы отключает все VM этой беседы; исправленный код требует нового запуска/экземпляра. `pcall`/`xpcall` не установлены.

Правила сочетаний:

- Не более одного сервиса в пакете, включая чтение профиля и отмену проверки выпуска.
- Триггеры нельзя сочетать с сервисом, close или завершением мини-игры.
- `ui.close` — последняя команда; несовместим с сервисом/завершением.
- Завершение мини-игры — единственное и последнее; несовместимо с сервисом/триггером/close.
- Изменение RNG добавляет одну служебную команду в начало: остаётся не более 255 других команд.
- Чистые чтения/описания и логирование после последней команды сами команду не создают; это не отменяет общий бюджет вычисления.

Атомарность пакета не означает транзакцию внешнего мира. После commit WAV может не открыться — придёт `audio_result/failed`; диск может отказать — `service_result/success=false`. Принятый вид и уже изменённая память профиля из-за такого отказа не откатываются. Уже опубликованный целый файл слота не удаляется поздней отменой. Диагностические логи намеренно независимы от игрового commit. Ранее успешно выполненные сценарные команды не откатываются при сбое следующего блока.

## Пространства имён, ID и специальные значения

| Значение | Сценарий game | Корневой ui-ресурс | ui-модуль |
| --- | --- | --- | --- |
| refs | имена → стабильные GUID из References блока/ресурса | имена холста → handles собственных узлов | пустая таблица; передавайте handles аргументами |
| modules | отсутствует | имена → GUID N объявленных Lua-импортов этого файла | собственные импорты файла |
| audio | отсутствует | имена → GUID N WAV из References корневого Lua-ресурса | отсутствует; передавайте ID аргументами |
| ui.null | отсутствует глобальная ui; null в game-результате остаётся непрозрачным маркером | неизменяемый userdata сериализуемого null | тот же маркер через ui |
| math.pi | отсутствует | константа числа π | отдельная таблица math с π |
| handlers | не используется | возвращаемая таблица on_event/on_load/input_events | модуль вместо handlers возвращает свою таблицу экспортов |

Имена refs/scripts: до 256 ссылок, длина имени <=128, идентификатор `[A-Za-z_][A-Za-z0-9_]*`; для графа модулей есть более строгие отдельные квоты. Переименование объекта не меняет его ID. Нельзя подставлять имя сцены/ресурса или путь вместо GUID. Имена примеров `helper.caption`, `puzzle.draw` и прочие авторские экспорты — не API движка.

Handle узла — непрозрачная строка с resource/instance/node, а не стабильный GUID проекта. Действителен только в живом экземпляре своего холста. Копия получает новые ID, удалённые ID не используются повторно до закрытия экземпляра. Одинаковый ресурс, открытый дважды, имеет несовместимые handles. Сохранить строку в state технически можно, но после восстановления она устарела: реконструируйте соответствие по refs/данным.

ID анимационного **описания** живёт один вызов обработчика. ID анимации/звука/сервисного запроса — корреляция операции своего владельца; не заменяет handle узла. `cancel_animation` для неизвестного корректного GUID — no-op; stop/volume звука для неизвестного ticket — ошибка; cancel_release_check чужого ID — ошибка. Нельзя переносить их между экземплярами/сеансами. Детали у каждой функции.

AuthorKey для trigger/persistent: `[a-z][a-z0-9_.-]{0,63}`; ID слота — другой формат, см. [хранилище](session-and-storage.md).

## Пауза, закрытие, сцены, сеансы и сохранения

Корневой холст сцены живёт вместе с ней. Слой имеет параметры модальности и паузы, заданные автором. Нет встроенных обязательных меню, P/F9/F-клавиш для проекта: действия назначаются в GUI. Во время паузы игровое время, сюжетные движения, анимации и группы звука удерживаются; уже готовый ui-пакет приостановленного владельца ждёт. Меню над ним может использовать другую VM той же беседы. Мини-игра приостановлена при любом верхнем слое; обычный экземпляр — при блокирующей паузе сверху/неактивном host.

Анимации стоят также при незавершённом пакете/очереди своего экземпляра. Для звука есть исключение: pending обычного update не останавливает уже проигрываемый поток; pending ввода/результата/load удерживает его. HTTP-проверка выпуска и её wall-clock deadline продолжаются в паузе, доставка ответа ждёт.

Смена сцены очищает её UI-экземпляры и связанные handles/state/RNG/input/операции. Сценарный низкоуровневый jump сохраняет переменные, время, состояния/размещения/показ персонажей и движения; очищает оставшуюся очередь и hotspots. Авторский вход фразы может затем изменить персонажей своими командами. GUI-команда входа в сцену использует отдельный reset сценарного состояния с сохранением переменных/времени. Не путайте эти пути.

NewGame, MainMenu, успешный Load и завершение сеанса инвалидируют прежних владельцев и pending-ответы. Ошибочный Load сохраняет прежний сеанс. Успешный Load атомарно принимает проверенный снимок без replay команд, Lua и продвижения времени; звук прежнего прохода остановлен, возобновляется фон сохранённой сцены, voice/effect фразы не повторяются. Обычный корневой ui-обработчик после Load прикрепляется отложенно при первом взаимодействии; произвольные экраны и их VM не восстанавливаются автоматически.

| Данные | Между ui-событиями | Обычный игровой слот | Профиль |
| --- | --- | --- | --- |
| locals/замыкания/глобалы/кеш модулей | да, в живой VM | нет | нет |
| game.set переменные, позиция, время, сценарные ожидания/очередь/движения | в сюжетном состоянии | да, с полной валидацией | нет |
| ui state/RNG обычного экрана | да, до закрытия | нет | нет |
| state/RNG/parameters активной разрешённой мини-игры, последний итог | да | да при барьерах | нет |
| дерево UI, capture/focus/keys, анимации, источники/позиции звука, сетевые операции/очередь UI | пока живы | нет | нет |
| настройки и persistent строки | независимо от экранов | нет | да, по результату записи |
| журнал и HTTP-кеш | в памяти host в своих пределах | нет | не данные profile.json; журнал может писаться отдельным файлом |

Не переносите locals/handles через слот. Для восстановления мини-игры храните только явные данные. Перезапуск F6 создаёт новое окружение; Load не является возвратом к старому Lua-стеку. Произвольного rollback нет.

## Восстанавливающий on_load мини-игры

После загрузки сохранённой мини-игры создаётся новая VM и вызывается on_load с сохранёнными state/RNG/parameters и `ui.is_restoring()==true`. `on_load` получает **пустую** таблицу e, не событие с полем restoring. Восстановление должно только построить представление из данных.

| Разрешено | Запрещено |
| --- | --- |
| get/get_state/minigame_parameters/is_restoring, find, стандартная библиотека, import, log | любые сервисы, trigger, close, complete/cancel_minigame |
| set_text/visible/enabled/geometry, create/remove/set_parent | capture/release/focus, play/stop/volume аудио |
| подготовка tween/sequence/parallel без запуска | animate/cancel_animation |
| set_state того же канонического значения; RNG без изменения итогового снимка | изменить сохранённый state или итоговый RNG |

Проверка сравнивает итоговое явное состояние и RNG, а не запрещает каждое чтение/вычисление по имени. Поэтому случайное число с точным восстановлением потока технически может пройти; авторский код должен просто отрисовать сохранённый результат и не делать новых выборок. Ограничения относятся именно к восстанавливающему load-пакету; последующие on_event восстановленного экземпляра работают нормально, хотя is_restoring остаётся true.

Источник и негативные тесты: [PrepareAsync](../../src/NovellMaker.Core/Screens/Lua/ScreenLuaSession.cs), [RestoreCannotChangeStateRngOrProduceEffects](../../tests/NovellMaker.Core.Tests/Screens/MinigameLuaTests.cs).

## Исходники, F6 и изоляция

Файлы Lua отслеживаются с debounce; диагностический разбор отменяется и проверяет актуальность текста. Изменение файла не подменяет код живой ui-VM. Следующий F6/экспорт захватывает новые исходники; F6 начинает новый сеанс. Сценарий с блоками запускается с начала, статический выбор фразы не исполняет Lua. Проверка синтаксиса не запускает обработчики, не проверяет их эффекты и не доказывает корректность поведения.

Парсер/VM работают в поставляемом runtime-worker до инициализации MonoGame. При отсутствии worker запуск запрещён; установленный SDK игроку не нужен. Preflight ограничивает код, coroutine-счётчик — Lua-инструкции, callbacks — отдельную работу, IPC — размер данных, host — число операций. GC heap worker ограничен 64 МиБ; Windows Job Object ограничивает committed memory процесса 256 МиБ и завершает его при закрытии job. Это **не полная ОС-песочница**. Аналога общей ОС-квоты памяти на Linux/macOS нет; подтверждённый нативный путь — Windows x64. Кроссплатформенность Core и тесты данных не означают проверенный нативный экспорт остальных ОС.
